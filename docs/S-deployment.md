# S. استقرار روی زیرساخت ایران — Deployment

> این سند مسیر رفتن از نمونهٔ فعلی به یک سرویس واقعیِ در حال اجرا روی سرور ایران است.
> فایل‌های اجرایی‌اش در پوشهٔ `infra/` و `server/` هستند.

---

## S.1 انتخاب زیرساخت

| لایه | گزینهٔ پیشنهادی | جایگزین | چرا |
|---|---|---|---|
| **سرور اپ** | ابر آروان (VPS) یا لیارا | پارس‌پک، ایران‌سرور | تأخیر پایین از داخل ایران، پرداخت ریالی، بدون ریسک تحریم IP |
| **پایگاه داده** | PostgreSQL 16 روی همان VPS یا سرویس مدیریت‌شدهٔ آروان | — | RLS برای جداسازی مستأجرها لازم است |
| **کش و صف** | Redis | — | نشست، محدودیت نرخ، صف کارهای پس‌زمینه |
| **ذخیرهٔ فایل** | آبجکت استوریج آروان (سازگار با S3) | فضای ابری پارس‌پک | ضبط کلاس و فایل تکالیف حجیم می‌شوند |
| **CDN و WAF** | ابر آروان | — | کش استاتیک، محافظت پایه، گواهی TLS رایگان |
| **سرور کلاس آنلاین** | BigBlueButton روی VPS جدا | سرویس BBB ایرانی | BBB منابع زیاد می‌خواهد؛ روی همان ماشین اپ نگذارید |
| **پیامک** | کاوه‌نگار + ملی‌پیامک (دوتایی) | SMS.ir، فراز | failover لازم است |
| **پایش** | Uptime Kuma + Grafana خودمیزبان | — | سرویس‌های خارجی پایش از ایران ناپایدارند |

### حداقل منابع

| سرویس | CPU | RAM | دیسک | یادداشت |
|---|---|---|---|---|
| اپ + پایگاه داده + Redis | ۴ هسته | ۸ گیگ | ۱۰۰ گیگ SSD | تا ۵۰ آموزشگاه |
| BigBlueButton | ۸ هسته | ۱۶ گیگ | ۲۰۰ گیگ SSD | حدود ۱۰۰ کاربر هم‌زمان |
| آبجکت استوریج | — | — | از ۵۰۰ گیگ | ضبط کلاس سریع پر می‌کند |

> **هشدار هزینه:** یک ترم ۲۰ جلسه‌ای ضبط‌شده برای ۴۰ کلاس، به‌راحتی چند صد گیگابایت
> می‌شود. سیاست نگهداری (بند Q.7) را از روز اول فعال کنید، نه بعد از پر شدن دیسک.

## S.3 گام‌های استقرار

```bash
# ۱) سرور را آماده کنید (اوبونتو ۲۴.۰۴)
ssh root@YOUR_SERVER
bash infra/bootstrap.sh          # داکر، فایروال، کاربر غیرروت، fail2ban

# ۲) متغیرها را بگذارید
cp infra/.env.example infra/.env
nano infra/.env                  # رمزها، کلید درگاه، توکن پیامک، کلید BBB

# ۳) بالا بیاورید
cd infra && docker compose up -d

# ۴) پایگاه داده را بسازید
docker compose exec app npm run migrate
docker compose exec app npm run seed:levels   # سری‌های کتاب آماده

# ۵) گواهی TLS
docker compose exec nginx certbot --nginx -d talkora.ir -d app.talkora.ir

# ۶) سلامت
curl -s https://app.talkora.ir/healthz | jq
```

فایل‌ها: `infra/docker-compose.yml`، `infra/nginx.conf`، `infra/bootstrap.sh`،
`infra/.env.example`.

## S.4 نکات ویژهٔ ایران

| موضوع | کاری که باید بکنید |
|---|---|
| **بدون وابستگی خارجی در زمان اجرا** | فونت، آیکون و اسکریپت همه self-host. در CI با بلاک‌کردن دامنه‌های خارجی تست کنید |
| **بیلد در محیط دارای تحریم** | `npm ci` روی سرور ایران ممکن است به رجیستری نرسد. **ایمیج را در CI بسازید و push کنید**، روی سرور فقط `pull` |
| **رجیستری داکر** | رجیستری داخلی (آروان/لیارا) یا mirror. Docker Hub از ایران ناپایدار است |
| **NTP** | ساعت سرور باید دقیق باشد؛ امضای درگاه و توکن یک‌بارمصرف به آن حساس‌اند |
| **timezone** | سرور روی UTC، نمایش روی `Asia/Tehran`. هرگز timezone سرور را تهران نگذارید |
| **بکاپ** | روزانه رمزنگاری‌شده روی آبجکت استوریج + یک نسخه خارج از همان دیتاسنتر. **هر سه ماه یک بازیابی آزمایشی** |
| **نماد اعتماد** | برای فعال‌سازی درگاه لازم است؛ فرایندش چند هفته طول می‌کشد، زودتر شروع کنید |

## S.5 امنیت پیش از انتشار

- [ ] فایروال فقط ۸۰، ۴۴۳ و SSH؛ پایگاه داده و Redis روی شبکهٔ داخلی داکر
- [ ] SSH فقط با کلید، بدون رمز، بدون ورود root
- [ ] `fail2ban` روی SSH و مسیر ورود
- [ ] محدودیت نرخ روی OTP: ۵ درخواست در ساعت به‌ازای شماره، ۲۰ به‌ازای IP
- [ ] هدرهای امنیتی: HSTS، CSP، X-Frame-Options، Referrer-Policy
- [ ] رمزها در فایل env با دسترسی ۶۰۰، هرگز در گیت
- [ ] **تست نشت بین مستأجرها** در CI (بند J.7)
- [ ] لاگ دسترسی بدون ذخیرهٔ کد ملی و شمارهٔ کارت

## S.6 اتصال کلاس آنلاین

### BigBlueButton

نصب روی VPS جدا:
```bash
wget -qO- https://ubuntu.bigbluebutton.org/bbb-install-3.0.sh | bash -s -- \
  -v jammy-300 -s bbb.talkora.ir -e admin@talkora.ir -g
bbb-conf --secret     # این کلید در .env می‌رود
```

فراخوانی‌های API که استفاده می‌کنیم — همه با چک‌سام SHA-1 امضا می‌شوند:

| فراخوانی | کِی | برای چه |
|---|---|---|
| `create` | ۱۵ دقیقه قبل از جلسه | ساخت اتاق با `record=true` و `meetingID` یکتا |
| `join` | لحظهٔ ورود | لینک امضاشده با نقش و `userID` مبهم ما |
| `isMeetingRunning` | حین جلسه | برای نوار زندهٔ حاضرین |
| `getMeetingInfo` | حین جلسه | فهرست شرکت‌کنندگان → حضور و غیاب خودکار |
| `end` | پایان | بستن اتاق |
| `getRecordings` | کارگر پس‌زمینه | یافتن ضبط آماده‌شده |

**وب‌هوک:** BBB افزونهٔ `bbb-webhooks` دارد. رویداد `meeting-ended` را بگیرید تا
لازم نباشد مدام poll کنید.

### Google Meet

- Google Cloud project، فعال‌سازی Meet REST API، حساب سرویس با
  **domain-wide delegation** روی دامنهٔ Workspace آموزشگاه
- `spaces.create` برای هر جلسه یک space جدا (یک کنفرانس فعال در هر space)
- **محدودیت‌هایی که باید به مشتری گفته شود:** شرکت‌کنندهٔ بدون اکانت Workspace
  فقط با نام خوداظهاری شناخته می‌شود، رکورد جلسه بعد از ۳۰ روز حذف می‌شود،
  و سقف ۶۰ درخواست در دقیقه است. یعنی **حضور و غیاب خودکار قابل اتکا نیست**
  (بند Q.2)

### اسکای‌روم و ادوبی کانکت
همان اینترفیس `MeetingProvider`؛ فقط یک کلاس جدید. فاز ۲.

## S.7 بارگذاری خودکار فایل ویدیویی

کارگر `recording-worker` این چرخه را می‌بندد. کد در `server/workers/recording.ts`.

```
جلسه تمام شد
   ↓
⚙ کار «واکشی ضبط» با تأخیر ۱۰ دقیقه در صف قرار می‌گیرد
   (BBB بعد از جلسه زمان می‌خواهد تا ضبط را پردازش کند)
   ↓
⚙ getRecordings(meetingID)
   ├─ هنوز آماده نیست  → تلاش دوباره با فاصلهٔ فزاینده: ۱۰، ۲۰، ۴۰ دقیقه … تا ۶ ساعت
   ├─ published=false   → publishRecordings برای آماده‌سازی
   └─ آماده             → ادامه
   ↓
⚙ دانلود از سرور BBB به‌صورت جریانی (فایل روی دیسک اپ کامل نمی‌شود)
   ↓
⚙ آپلود چندبخشی به آبجکت استوریج، مسیر:
   institutes/{institute_id}/recordings/{term}/{class}/{session}.mp4
   ↓
⚙ ثبت در ONLINE_SESSION: recording_url، مدت، حجم، تاریخ انقضا
   ↓
⚙ اگر سیاست آموزشگاه «انتشار خودکار» باشد:
     ضبط برای زبان‌آموزهای همان کلاس قابل پخش می‌شود + اطلاع‌رسانی
   وگرنه: در صف تأیید مدرس می‌ماند
   ↓
⚙ بعد از تأیید موفق آپلود، ضبط از سرور BBB حذف می‌شود تا دیسکش پر نشود
   ↓
⚠ اگر بعد از ۶ ساعت آماده نشد: به مدرس و مدیر اطلاع داده می‌شود.
   هرگز بی‌صدا شکست نمی‌خورد.
```

**نکات عملی:**
- دانلود و آپلود **جریانی** باشد، نه بارگذاری کامل در حافظه
- کلید `idempotency` روی `online_session_id` تا اجرای دوباره، فایل تکراری نسازد
- لینک پخش برای زبان‌آموز، **امضاشده و کوتاه‌عمر** (۳۰ دقیقه) باشد، نه لینک مستقیم استوریج
- پهنای باند خروجی را در ساعات اوج محدود کنید، وگرنه آپلود ضبط، کیفیت کلاس‌های
  در حال برگزاری را خراب می‌کند
- اگر آموزشگاه سهمیهٔ فضایش پر شده، آپلود متوقف و به مدیر هشدار داده می‌شود —
  ضبط روی BBB می‌ماند تا تصمیم بگیرد

## S.8 ورود با کد یک‌بارمصرف

پیاده‌سازی در `server/auth/otp.ts`.

| قاعده | مقدار |
|---|---|
| طول کد | ۵ رقم |
| اعتبار | ۲ دقیقه |
| ذخیره | فقط **هش** کد در Redis با TTL، نه خود کد |
| تلاش اشتباه | حداکثر ۵ بار، بعد کد باطل می‌شود |
| ارسال دوباره | حداقل ۶۰ ثانیه فاصله |
| محدودیت نرخ | ۵ در ساعت به‌ازای شماره، ۲۰ در ساعت به‌ازای IP |
| خط ارسال | **خدماتی**، نه تبلیغاتی (بند P.4) |
| پاسخ سرور | برای شمارهٔ موجود و ناموجود **یکسان** — تا فهرست کاربران قابل استخراج نباشد |
| نشست | توکن کوتاه‌عمر + refresh چرخشی؛ با تغییر نقش باطل می‌شود |

## S.9 چه چیزی هنوز نیست

صادقانه: `server/` یک **اسکلت کارآمد** است، نه محصول کامل. این‌ها هست:
اسکیمای پایگاه داده با RLS، ورود با OTP، آداپتور BBB و Meet، کارگر ضبط،
و فایل‌های استقرار.

این‌ها نیست و باید نوشته شود: بقیهٔ CRUD، اتصال درگاه پرداخت، تولید فاکتور،
موتور گزارش، و رابط کاربری متصل به API (نمونهٔ فعلی هنوز با دادهٔ ثابت کار می‌کند).
